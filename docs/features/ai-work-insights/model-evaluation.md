# Work classifier measurement (W3)

Which pretrained model, if any, labels the kind of work on the device (decision 5: evaluate first, on-device only). No model was fine-tuned. Each candidate embeds a message as published, and the kind of work comes from comparing it with prototype phrases written for the classifier (`apps/server/src/insights/work-prototypes.ts`).

Reproduce:

```sh
uv pip install -r apps/server/scripts/insights-model/requirements.txt
cd apps/server
bun scripts/insights-model/export.ts > .insights-models/eval-data.json
python scripts/insights-model/evaluate.py .insights-models/eval-data.json
```

**Result: no candidate meets the bar, so no model ships.** The best one, `multilingual-e5-small` with a linear head, names a kind of work correctly 72% of the time. The bar is 85%. Below the bar, a model would mislabel roughly one session in four, and hours back, step anatomy and every kind-of-work chart would carry that error without saying so. Until a candidate passes, sessions are sent without a kind of work, and the console shows them as "Not labeled". That's what the design said should happen.

## Set-up

- **Evaluation set:** `src/insights/eval/work-samples.ts`. It has 296 first messages (128 English and 128 Korean plain ones, plus 40 hard cases), reviewed by a Korean speaker in #126.
- **Prototypes:** 114 phrases, 6 per kind of work split across both languages, plus phrases for learning and for things that aren't work. They're written separately from the evaluation set, and `work-prototypes.test.ts` fails if any prototype appears in it.
- **Two methods per model:**
  - *nearest*: the kind of work whose three closest prototypes are most similar, unless that isn't better than "not work" by a margin;
  - *head*: softmax regression trained on the prototypes only, which answers only when it is at least as confident as a floor.
- **Margin and floor:** both are chosen by leave-one-out on the prototypes and never tuned on the evaluation set, so the scores below were measured on unseen messages.
- **Runtime:** onnxruntime 1.30 on CPU with 2 threads, using each repository's own int8 export.

**Bar**, written down before the first run:

| Measure | Required |
| --- | --- |
| Precision on named kinds of work | 85% or more |
| Coverage (share of work messages given a kind) | 70% or more |
| Abstention on not-work and vague messages | 70% or more |
| Korean precision, compared with English | No more than 10 points lower |
| Model size | 120 MB or less |
| Speed | 50 ms or less per message |

The confusions show why. The kinds of work that miss are the neighbouring ones:

- **Engineering:** fix → test and code → test.
- **Writing:** design → copy, email → copy and hr → summ.
- **Analysis:** analyze → research.

Crew's 16 kinds of work are fine-grained within each family. A message's first sentence often doesn't decide between, say, fixing a bug and writing the failing test.

Findings along the way:

- **Plain similarity is not enough.** Every model named a kind of work for most messages but got about one in three wrong. The linear head cuts errors by being willing to say nothing; e5-small's head abstained on every not-work message.
- **Korean is not the problem.** For every e5 candidate, Korean precision is within a few points of English, and at or above it for e5-small.
- **The larger model buys coverage, not precision.** e5-base covers 13 points more than e5-small's head at about the same precision, at more than twice the size.

## What would pass

These are listed in the order I'd try them. Each needs the same measurement before it ships.

1. **Classify the family first, then the kind of work only when sure.** Write, sheet, code and design are far apart. A two-level answer (always the family, the kind only above a floor) would give the console reliable families. The console already slices by family through "What it produced".
2. **More prototypes, written by people in each function.** 6 phrases per kind of work is thin. The confusions concentrate in a few pairs, and each pair needs phrases that separate it.
3. **Use more than the first message.** The structural labels already know whether tests ran (code against test) and whether a connector sent something (email against copy). The classifier could take them as inputs.
4. **A fine-tuned head on labeled examples.** This needs a training set separate from the evaluation set, which in practice means synthetic messages written for training.

## Round 2: a training set (2026-10-08)

The first round's limit was data: 114 prototype phrases. Round 2 adds a hand-written training set (`src/insights/train/`) of 1,060 first messages: 30 per kind of work in each language, plus 25 learning and 25 not-work examples per language. `train.test.ts` fails if any of them is, or contains, an evaluation message. The head is trained on the training set and the prototypes at two levels, the family (write, sheet, code, design, or not work) and the kind of work. Confidence floors come from 5-fold cross-validation on the training data. The evaluation set is embedded once, at the end, and only scored.

Reproduce: `python scripts/insights-model/train.py .insights-models/eval-data.json`.

These numbers use onnxruntime's basic graph optimisations only. A first run used the default, extended fusions, and scored the e5-small family at 87.9%; but those fusions change int8 results between onnxruntime versions, so redrob-server (onnxruntime-node 1.23) did not reproduce the embeddings the head was trained on (3 of 296 labels differed). Basic optimisations are exact, so the head was retrained on them.

**Result: the family level ships, on multilingual-e5-small.** The kind of work does not yet. On the small model it is 5 points under the bar. On the base model it is 0.9 points under, and at 278 MB it is over the size limit as well.

One caveat about the floors. Cross-validation on the training data reached 85% precision at the lowest floor tried (0.05), so the floor filters nothing: the model is more certain on training-style messages than on evaluation ones. The floor is not tuned on the evaluation set, because that would make the score above meaningless. The family result passes with that floor anyway. Before the kind of work ships, the training set needs a held-out slice written in the evaluation set's style, so a floor can be chosen on data that looks like real use.

Next for the kind of work, in order: more training messages for the pairs that are still confused, a held-out slice for the floor, then the structural inputs (tests ran, something was sent, the type of file written).

Reusing the encoder Cowork already ships for Redrob Auto's route labels (distiluse-base-multilingual-cased-v2, `packages/route-labeller`) would add nothing to the download, so it was measured the same way: 84.5% family precision and 72.0% for the kind of work, both under the bar. The second model is the price of the family level passing.

### In the app

redrob-server runs the family head in `src/insights/work-classifier.ts`: its own SentencePiece tokenizer (`unigram.ts`, which gives the same ids as Hugging Face `tokenizers` on all 1,484 training, evaluation and edge-case texts), the pinned encoder from `apps/desktop/resources/insights-model`, and `work-head.json` from `train.py`. On the 296 evaluation samples it gives the same label as the Python reference on all 296; confidences differ by under 1e-6. A label takes 4.4 ms (median), and loading the model takes under a second.
