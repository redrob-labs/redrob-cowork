---
title: "Diagnostic prompts"
description: "Paste-able prompts that let your agent debug Redrob Work issues on its own."
---

When something in Redrob Work looks wrong, the fastest debugger is usually the agent
itself: it can read its own configuration, probe the local server, and verify fixes
in-band. This page collects paste-able diagnostic prompts. Copy the whole block for your
situation into a chat and let the agent work through it.

Each prompt is safe by default: it gathers evidence first, redacts secrets, and asks
before changing anything.

If the symptom is DNS, TCP 443, TLS chain, or proxy reachability, start with
[Network diagnostics](/start-here/network-diagnostics) instead.

<Note>
Everything below is local. Redrob Work is a desktop app plus a local `redrob-server`
running the Redrob Code engine as a sidecar. There is no account and no remote control
plane to check, so every probe stays on your machine.
</Note>

## 1. An MCP server is connected, but its tools are missing

**Symptoms**

- `Settings > Library` shows the MCP connection as ready, but the agent never calls its
  tools.
- The agent answers from documentation instead of acting in the connected system.
- The agent claims a tool is "conceptual" rather than callable.

**What is usually wrong**

Redrob Work writes a generated `runtime-opencode-config.json` and passes it to the
engine as `OPENCODE_CONFIG`. A task holds the tool set it started with, so a connection
added or repaired after the task began is not visible to it. Less often the generated
config never reached the engine, or a tool-deny policy is filtering the tool out.

**Paste this to your agent**

````text
Diagnose whether my MCP server's tools are actually available in this workspace. Gather evidence only: do not modify configuration, authenticate, log out, remove anything, or restart services. Never print configuration-file contents, bearer tokens, Authorization values, cookies, API keys, or local server tokens.

Replace <server-name> with the connection name shown in Settings > Library.

## Phase 1 - Test the task's actual tools

1. Attempt to call one tool from `<server-name>` with a harmless read-only argument. Do not substitute documentation and do not explain alternatives. Record whether the runtime accepts the call, and its exact non-secret result or rejection.
2. Attempt to call `redrob_extension_list_actions`. Record whether the runtime accepts the call. Do not infer availability by asking yourself to "list your tools"; models omit and invent tools.

## Phase 2 - Find the engine and its generated config

3. Detect whether this machine is Windows, macOS, or Linux.
4. Find the exact Redrob Code executable the desktop app is using. It is named `redrob`, and it is either the packaged sidecar under the app's `resources/sidecars` directory or the path in `REDROB_CODE_BIN`. Do not assume an unrelated binary on `PATH` is the same one.
5. Find the generated `runtime-opencode-config.json` beside the active `server.json`. Respect any discovered `REDROB_SERVER_CONFIG`, `REDROB_RUNTIME_DB`, or XDG overrides. Typical locations:
   - Windows: `%APPDATA%\redrob\runtime-opencode-config.json`
   - macOS and Linux: `${XDG_CONFIG_HOME:-$HOME/.config}/redrob/runtime-opencode-config.json`
6. Report whether it exists and its last-modified time. Never display, copy, parse, or summarize its contents: it can contain Authorization headers.

## Phase 3 - Run a safe fresh-process probe

7. From this workspace root, set `OPENCODE_CONFIG` to the discovered runtime config for the subprocess only, then run:
   - `<exact-engine-executable> --version`
   - `<exact-engine-executable> mcp list`
8. Do not run `mcp add`, `mcp auth`, `mcp logout`, `debug config`, or anything that changes or prints configuration. Do not pass `--print-logs` if it could expose headers.
9. Report:
   - operating system
   - engine executable path and version
   - runtime config path, existence, and last-modified time
   - whether `<server-name>` is listed
   - its exact status and non-secret error
   - whether this workspace is the primary managed workspace or a secondary one

Important: `mcp list` starts a fresh process. Do not claim it attaches to the engine already running inside Redrob Work. Describe it only as a fresh-process probe using the same binary and generated config.

## Phase 4 - Classify the result

- Fresh probe omits `<server-name>`: the generated config is missing, the wrong config was selected, or this is a secondary workspace whose MCP servers are registered dynamically.
- Fresh probe reports `failed` or `needs_auth`: keep the exact non-secret error and investigate the endpoint, credential, or TLS chain.
- Fresh probe reports `connected` but Phase 1 rejected the tool: the stored endpoint works and the live task has a stale tool snapshot.
- Both Phase 1 calls rejected: investigate whether the running engine loaded the injected config and plugins, plus project and global tool-deny policy.
- Forced call works but a natural request chooses documentation: exposure is healthy; this is system-prompt steering.

Finish with a concise redacted report.
````

**Then verify inside Redrob Work**

1. Open `Settings` > `Library` and click `Refresh`.
2. Find the connection and expand it. Keep its status and non-secret error: `Ready`,
   `Issue`, `Sign in needed`, `Offline`, or `Paused`.
3. Open the command palette and run `Reload OpenCode config`.
4. Start a **new** task in the same workspace so it picks up the current tool set.
5. Repeat the forced tool call from Phase 1.

**How to interpret both results**

| Fresh `mcp list` | In-app status and forced call | Likely boundary |
| --- | --- | --- |
| Missing or failed | Missing or failed | Generated config, endpoint, credential, or TLS |
| Connected | In-app status failed | Live engine registration or workspace routing |
| Connected | In-app Ready, forced call rejected | Stale task tool snapshot or engine compatibility |
| Connected | Forced call succeeds, natural request uses docs | Agent steering rather than tool exposure |

## 2. No models, or the Redrob Key looks disconnected

**Symptoms**

- The model picker is empty, or the Redrob provider is missing.
- A request fails with an authentication error against the model provider.
- You pasted a Redrob Key and the connect screen still says it is not connected.

**What is usually wrong**

The Redrob Code engine owns the Redrob Key. Redrob Work hands the key to the engine and
keeps no copy of it, so the engine's own auth store is the only source of truth. A key
that was never accepted, was rotated in the console, or was saved while the engine was
unreachable produces exactly this symptom. The engine also fetches the model catalog
from `console.redrob.ai` itself, so a blocked host looks identical to a bad key.

**Paste this to your agent**

````text
Diagnose why no models are available in this workspace. Gather evidence only: do not rotate, delete, or print any credential. Never echo a key value, an Authorization header, or anything that looks like an API key. Report only whether a credential is present, never what it is.

## Phase 1 - Evidence

1. Report the desktop app version and the Redrob Code engine version. The pinned engine version is in `constants.json` as `redrobCodeVersion` at the repo root of a source checkout; in an installed app, report what the app's own status surface shows.
2. Report whether the local `redrob-server` is running and reachable, and on which loopback port.
3. Report whether the engine reports a Redrob credential as connected. Do not read credential files directly; use the app's status surface.
4. Report whether `REDROB_API_KEY` appears anywhere in the environment-variable store. It should not: that store rejects the name on purpose, because the engine is the only place the key lives.

## Phase 2 - Probe the catalog host

5. Check whether `console.redrob.ai` resolves and whether TCP 443 to it completes. Report the result without sending a credential.
6. If a proxy or custom CA is in play, report which one, from configuration only.

## Phase 3 - Classify

- Engine reports no credential: the key was never accepted. Paste it again on the connect screen and watch for a confirmation.
- Engine reports a credential but requests fail with an authentication error: the key was revoked or rotated at console.redrob.ai. Issue a new one and paste it again.
- `console.redrob.ai` is unreachable: this is a network or proxy problem, not a key problem. See Outbound network access.
- Engine and host are both fine but the picker is empty: reload the engine config, then start a new task.

Finish with a short report naming the single most likely boundary.
````

**Then verify inside Redrob Work**

1. Reissue a key at [console.redrob.ai](https://console.redrob.ai) if the engine reports
   no credential, and paste it on the connect screen.
2. Confirm the connect screen reports success. If it does not, the engine did not accept
   the key and nothing was stored.
3. Start a new task and open the model picker.

If the agent completes all phases and verification still fails,
[open an issue](https://github.com/redrob-labs/redrob-work/issues) and paste the agent's
final report. It is already redacted.
